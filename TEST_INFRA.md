# ReloGo Supabase API Integration Testing Infrastructure

This document details the architecture, design principles, test case methodology, and execution instructions for the ReloGo Python integration test suite.

---

## 1. Objective and Scope

The suite validates selected ReloGo backend contracts against a fresh local
Supabase stack, primarily through the API gateway at
`http://127.0.0.1:54321`. It also contains a smaller set of pure-Python
requirement simulations for checklist selection and local-only PII/PDF state.
Those simulations do not exercise the mobile implementation, secure storage,
or PDF renderer. This suite is therefore an API integration/E2E-style gate,
not full-platform browser, mobile-device, or hosted-environment E2E coverage.

The scope covers:

- Waitlist signup flow, constraints, and throttling.
- Anonymous onboarding, policy-consent state/acceptance, and profile creation.
- Checklist generation, corridor matching, and dynamic deadline calculations.
- Progress tracking, state updates, and updates persistence.
- Schema-level PII protection plus simulated local PII/PDF cache behavior.
- Support thread lifecycle, fixed-question constraints, reply-persistence RPCs,
  and human takeover.

## 2. Test Infrastructure Architecture

The suite is written in **Python 3.11** using **pytest** and the official
**supabase** Python package. Direct dependencies are pinned in
`tests/e2e/requirements.txt` so local runs and CI use the same compatible
versions.

### Architecture Components

1. **Client Isolation**: The test runner instantiates distinct Supabase clients representing different actors:
   - **Anonymous / Authenticated Client**: Emulates the mobile or web client.
   - **Service Role Client (Admin/Bypass)**: Provides privileged API setup,
     teardown, seeding, and out-of-band assertions.
2. **Transactional Cleanliness**: Since Supabase doesn't natively support rolling back transactions across API boundaries, the E2E suite uses explicit teardown fixtures to delete created test users, waitlist entries, support threads, and profiles.
3. **Fixed-Question Sync**: Validates that all support message inserts conform to the allowed set of 6 questions defined in migration 010.
4. **Boundary Classification**: Supabase-backed cases exercise real local Auth,
   PostgREST, RLS, triggers, and RPCs. Tests built from in-memory dictionaries
   or byte strings are requirement simulations and are not described as
   full-platform E2E validation.

## 3. Test Case Design Methodology

Pytest collects **exactly 85 test cases** across four logical test files. Cases
72–82 are focused server-policy consent integration tests (72–76 cover the
consent-state RPCs and version enforcement; 77–82 adversarially cover migration
019's consent gate on a user's own data, the `has_current_policy_consent()`
RPC, the `status <> 'HUMAN'` self-assignment guard, `accept_current_policies()`
idempotency, and the gate-opening transition). The remaining cases follow the
original four-tier feature organization, including three waitlist
signup-feedback cases for migration 022's enumeration-safe `accepted`/
`throttled` status.

### Tier 1: Feature Coverage (>= 5 tests per feature)

Verifies the core happy-path requirements of the 6 features.

1. **Waitlist**: Basic signup, validation of valid email & corridor formats.
2. **Auth/Consent**: Anonymous login, current-version profile creation, and
   authenticated policy-state behavior.
3. **Checklist/Deadlines**: Generation of corridor rules, mapping of vehicle and dependent tasks.
4. **Progress**: Toggling task status between AVAILABLE and COMPLETED.
5. **PII/PDF**: Schema checks plus in-memory simulations of local secure storage
   and filled-PDF caching lifecycle.
6. **Support AI Chat**: Thread creation, fixed question posting, and AI response persistence.

### Tier 2: Boundary & Corner Cases (>= 5 tests per feature)

Exercises the edge cases, validation boundaries, and adversarial security constraints.

- Waitlist signup duplicates, throttle limits, and SQL injection payloads.
- Profile moves with past dates, invalid provinces, and unauthenticated writes.
- RLS boundaries (users accessing other users' profiles/support threads).
- Fixed-question strictness: rejecting free-text user messages or unauthorized questions.
- Support thread status lock: preventing AI response when human takeover is active.

### Tier 3: Cross-Feature Combinations (Pairwise Coverage)

Evaluates interactions between features (6 tests).

- Waitlist signup transition to onboarded profile.
- Checklist generation changes when user modifies profile mid-move.
- Support questions reflecting checklist status.

### Tier 4: Real-World Application Scenarios (5 tests)

Exercises multi-step local API journeys; it does not drive the mobile UI.

- Scenario A: Standard User Onboarding, Checklist Completion, and Sign-out.
- Scenario B: High-Risk Move (Vehicle & Dependents), Custom Deadlines, and
  support reply persistence.
- Scenario C: Rule Update Scraping Alert and Admin Approval Flow.
- Scenario D: Privacy Hardening Verification (Account Deletion & Data Wipe).
- Scenario E: Concurrent Support Thread Racing and Human Takeover.

### Focused Policy-Consent Integration (5 tests)

Exercises migration 019 through authenticated/unauthenticated Supabase clients:

- Consent state with and without a profile.
- App-data RLS denial before current consent.
- Rejection of omitted and stale consent versions during profile creation.
- Server-current acceptance and server-authored consent timestamps.
- RPC authentication and missing-profile boundaries.

## 4. Execution and Verification

### Prerequisites
Install Docker, Supabase CLI `2.107.0`, and Python 3.11. From the repository
root, create an isolated environment and install the pinned test dependencies:

```bash
python3.11 -m venv .venv
source .venv/bin/activate
python -m pip install -r tests/e2e/requirements.txt
```

Start the local Supabase stack:

```bash
supabase start
```

### Running the Test Suite
Run the suite from the repository root. **This command resets the local
Supabase database** before the tests, so do not run it against local data you
need to preserve.

```bash
python -m pytest tests/e2e/ --strict-markers -ra
```

The session fixture also applies E2E-only grants after the reset. Before
running pgTAP privilege assertions or inspecting the normal local permission
model in the same stack, run `supabase db reset --local` again. CI runs the
integration and database jobs on separate isolated runners, so their state
does not overlap.

The `e2e-test` job in `.github/workflows/ci.yml` performs the same flow on an
isolated GitHub-hosted runner: it installs the pinned Python dependencies and
Supabase CLI, starts a fresh local stack, and executes all 85 cases. It requires
no GitHub or hosted Supabase secrets.

This integration verification is a mandatory quality gate before release
approval, alongside platform-specific mobile, landing, database, and manual
device/browser checks.
